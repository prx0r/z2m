# Judge Model

Treat judging as a constrained information channel. A judge commonly sees title/tagline, screenshots, Devpost copy, demo video, live demo, README, then code/CI only if interested. Deliberation happens from memory, so every surface must reinforce the same thesis.

Recurring criteria across hackathons:
- originality / concept
- technical execution
- sponsor/tool integration
- usability / presentation
- potential impact / feasibility
- completeness/progress

## Evidence matrix
| Criterion | Weak | Strong |
|---|---|---|
| Originality | adjectives | distinct insight + primitive |
| Technical | architecture prose | working E2E + CI + failure tests |
| Sponsor | SDK import | causal calls + trace + removal test |
| Presentation | polished visuals only | uninterrupted understandable workflow |
| Impact | generic TAM | specific repeated painful decision + wedge |
| Feasibility | roadmap | deployed API/state machine/receipt |

## Memory test
If the judge remembers eight words, choose them intentionally. The quotable sentence should sit near the central transformation.
